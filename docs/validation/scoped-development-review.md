# SDD 개발·검증 효율화 2차 구현 대조

검증일 2026-11-27. 사용자 선택 설계 1.2, Core 0.5.1 Patch. 이전 설계 1.1·Core 0.5.0의 D01~D10·필수 Gate·상태·UUID·공식 계약은 유지한다. 설계·정책 구현과 실제 에이전트 의미 판단 검증은 구분한다. Git 작업과 사용자 demo 업데이트는 실행하지 않았다.

## 차이 분석과 확정 반영

| 정책 | 기존 상태 | 이번 설계·구현 |
| --- | --- | --- |
| 11 테스트 수준 | 기존 Gate가 실제 argv·결과·시간·증거를 관리. 최소 충분 테스트 방식은 미상세 | [검증](../design/06-verification.md): L1 in-process/L2 실제 의존/L3 live/L4 E2E. 위험·분석 깊이와 독립, 필요 이유·운영 안전·자기 프로세스 정리. 공통 develop Skill에 반영 |
| 12 테스트 코드 | 기존 검사 재사용은 구현, 변경 유형별 검증 공백 기준 부족 | 신규·확장·결함·리팩터링·API·데이터·문구별 재사용/회귀 기준. 프로젝트 TDD·강도 유지, 자동화 우선·실행 불가 이유 기록 |

| 14 변경분 정합성 | 기존 소견·Gate/증거 사용 가능 | [검증](../design/06-verification.md): 필요한 관계 선택, 영향받은 미수정 계약·호환·소비자·사용자 변경 구분, 필요한 전체 범위 확장 |
| 15 문서 최소화 | records.py의 같은 바이트 쓰기 생략과 선택 갱신 구현 | [산출물](../design/01-artifact-model.md): 문서별 정보 변화 조건·No Extra Report·원형/식별자 보존. 공식 필수 쓰기는 유지 |
| 16 사실 재사용 | Work Item·findings·Evidence·현재 Gate Fingerprint 구현 | [영향 분석](../design/05-impact-analysis.md): 같은 요청의 사실 재사용, 변화별 재분석·재개/컨텍스트 유실 기준. 분석 캐시·중간 파일 없음 |
| 17 공식 호출 | 기존 최소 단계·official_step·유효 결과 계약 구현 | [공식 연동](../design/spec-kit-integration.md): 유형별 필요 검토, 실제 호출 시 전체 필수 범위·원형 유지. Analyze/Converge 목적·중복 분석 구분 |

정책 11~17의 선택은 Skill 의미 판단이다. Core는 이를 소스 의미 분석 로직이나 테스트 수준 영구 필드로 구현하지 않는다. 새 Baseline·스키마·명령·문서 인덱스·컨텍스트 엔진·검증 엔진은 없다. 필요한 Core 변경은 공통 Skill 변경을 정확히 설치하는 버전·알려진 번들 해시·누적 0.5.0→0.5.1 경로뿐이다.

## 구현 파일과 호환성

- src/sdd_core/skills/sdd-develop.md: 관련 범위·종료, 최소 충분 테스트·회귀, 변경분 관계, 사실 재사용, 쓰기 조건·공식 선택 정책을 한 번씩 추가. 양쪽 bundle()은 같은 본문을 설치한다.
- src/sdd_core/version_sync.py, __init__.py, pyproject.toml, monitor/pyproject.toml: Patch 일치와 기존 누적 변환 경로. 기존 tests/test_version_sync.py에 일곱 Baseline 파일 바이트 보존·버전 불일치 차단·승인 업데이트 검사를 추가했다.
- 기존 게이트 실행·정의·PASS·Fingerprint·필수 절차·complete·No Change No Write를 재사용했다. scripts/benchmark-verification-profiles.py는 0.5.1도 기존 0.5 기능 경로로 비교하도록 버전 조건만 수정했다.
- scripts/compare-scoped-development.py는 제품 런타임 기능이 아닌 명시 실행하는 임시 계약 비교 fixture다. 테스트·측정 원자료를 [함께 보존](scoped-development-measurements.json)한다.
- 기존 원본 01/04/05/06·architecture·Spec Kit·runtime·version-sync·profiles에 분산 책임을 유지했다. 결정 ST-39~43·백로그·CHANGELOG와 가이드·통합 진입점·HTML을 연결했다. 상세 명세를 새 문서에 중복 작성하지 않았다.

실제 설치된 공식 Spec Kit 1.4.0 Analyze·Converge 본문을 대조했다. Analyze는 tasks 이후 읽기 전용이며 후속 개정은 별도 판단, Converge는 tasks/implement 뒤 보완 tasks를 추가한다. 공식 Skill·Preset·Extension은 수정하지 않았다. 현재 고정 공식 버전 변경도 없다.

공식 specify-cli 1.4.0 전용 환경에서 Codex·Claude 각각 install→update를 실행해 complete/공식 상태 ok/Core 0.5.1/일곱 Baseline 파일을 확인했다. 이는 설치 연동 확인이며 모델이 공식 Skill을 실제 수행한 시험은 아니다. 실제 Core 0.5.0 소스로 만든 완료 프로젝트를 승인 변환했고 필수·품질 검사 통과 및 일곱 Baseline·앱·테스트의 바이트 해시 보존을 확인했다. schema migration은 없고 실패 재개·자동 원복을 추가하지 않았다.

## 실행 시나리오와 검증 한계

Core 회귀 100개, Monitor 26개 중 25개 통과·Windows 전용 1개 생략을 확인했다. 문서 JSON 예제 13개 실행, Markdown 구조·링크 29개와 설계 릴리즈 노트 1.2 추출, 공통 Skill quick_validate를 확인했다. HTML 3종은 데스크톱/모바일 Chrome 실행·JS 오류 없음과 기능목록 화면을 확인했고 생성 가이드 일치 검사도 통과했다. 뒤의 실제 모델 판단은 이 통과 수로 대체하지 않는다.

| 지시서 | 실행 근거·판정 |
| --- | --- |
| T01·T02 | 600개 기존 요구가 있는 Feature에서 실제 결함 assertion 실패→수리 PASS, 국소 확장은 관련 spec 절만 추가. plan·다른 Feature·사용자 파일 보존 |
| T03 | 기존 선택 갱신·같은 바이트/mtime 유지 테스트 통과. 실제 모델이 리팩터링에 불필요한 쓰기를 하지 않는지는 미확인 |
| T04 | 기존 신규 Feature profile/Discovery/specify 의무·등록·분리 및 상태 테스트. 모델의 공식 산출물 생성 PoC는 미확인 |
| T05·T06·T07 | 직접 소비자 실제 실행과 scope 확대 승인, 기존 의존·차단·Strict 상향 테스트. 실제 광범위 그래프 탐색 판단은 미확인 |
| T08 | HTTP loopback 임시 서버·실제 요청·응답 assertion, 실패/성공 뒤 finally에서 소유 서버 종료. 이것을 L1 검사로 대체하지 않음 |
| T09 | DB/Redis 환경을 새로 설치·실행하지 않았음. 실제 외부 의존 시스템과 수준 선택 PoC는 미검증 |
| T10·T11·T12 | 회귀 테스트를 먼저 실행해 결함 검출, 수정 후 관련 검사 재실행·동일 요청 세 번째 호출 reuse. 계약 변경의 profile/의무·무효화 검사 |
| T13·T14 | 공식 설치 본문·명령/절차 기록·필수 완료 차단 테스트. 모델의 실제 Analyze/Converge 호출·개정 처리는 미검증 |
| T15·T16 | 기존 stale 입력/증거·선택 refresh·suspended 재개·공식 필수 검토 입력 변경 차단 테스트 |
| T17·T18·T19 | 기존 사용자 파일 바이트 보존, mandatory 누락/약화·핵심 UNKNOWN/CONFLICT·Strict 자동 경로 차단 테스트. 실제 모델의 필수 전체 테스트 선택은 미확인 |
| T20 | 기록된 동일 목적/입력·증거만 공식 결과 활용, 다른 목적/Work Item PASS 승계 차단. 모델의 중복 의미 분석 감소는 미측정 |

문구 존재 검사를 정책 실행 검증으로 취급하지 않았다. 비교 fixture의 분류·절차 기록은 명시적인 테스트 입력이며 실제 모델의 의미 분류·공식 명령 실행 사실이 아니다.

## 전후 비교

개선 전 소스를 작업 시작 시 별도 보존했다. 동일 Python·초기 파일·요구·실제 검사로 단순 버그/국소 확장/API 계약/복수 Feature/live 연결의 5개 시나리오를 양쪽 설치 유형에서 2회씩 수행했다. 버전별 20회 모두 의도한 AssertionError를 검출하고 수리 후 완료했다. 이전 방식에 근거 없는 서버·보고서·분석 비용을 억지로 부과하지 않았다.

이 결과는 계약 보존·실제 결함 검출·필요한 live 실행의 근거다. 이번 Skill 정책으로 전체 개발·분석·토큰 비용이 감소했다는 실측 주장은 하지 않는다. 그 평가는 같은 모델의 네이티브 전후 실행이 필요하며 기존 ST-O1·ST-O7에 남긴다.

## 재대조와 남은 범위

11~17 설계·공통 Skill·기존 Core 계약 연결은 반영했다. 별도 정책 선택은 남지 않았다. 네이티브 Codex/Claude 의미 판단 T01~T20·외부 DB/Redis·실제 전체 시간/토큰 비교는 완료가 아니다. 설계와 구현을 실제 운영 검증 완료로 합쳐 보고하지 않는다.

작업 시작부터 존재하던 Monitor Reader/CEO 변경과 작업 중 추가된 같은 영역의 변경은 보존했다. 해당 별도 기능의 승인 정책·구현 완료를 이번 효율화 작업의 결과로 주장하지 않는다. 따라서 전체 Git diff에는 다른 작업의 파일도 포함될 수 있다. 최종 반영 시 기능별 변경 범위를 구분한다.
