# 제품 구현과 설계 대조 반복 절차

설계 1.0. 사용자가 SpecThread를 설계서 기반으로 구현·완성해 달라고 요청하면 이 절차를 적용한다. 대상 프로젝트에서 실행하는 별도 오케스트레이터나 자동 Git 기능이 아니라 **SpecThread 제품 저장소를 개발하는 AI의 작업 규칙**이다.

## 입력과 출력

입력은 [주제별 원본](README.md), [결정](DECISIONS.md), [백로그](OPEN-ISSUES.md), 현행 Core·Skill·스키마·CLI·테스트다. 출력은 구현 변경, 실행 검증과 설계 요구별 코드·테스트 대응표, HTML을 포함한 문서 및 남은 차이 보고다.

## 반복 순서

1. 요청 범위의 확정 요구를 원본의 절·결정 ID로 나눈다. 입력·출력·저장 필드·실행 순서·Gate·정상/실패·중단/재개·승인·기존 자료 보존·명시적 제외를 확인한다. 문서가 간단해졌다는 이유로 조건을 추정하지 않는다.
2. 기존 코드·Skill·테스트와 비교해 구현됨/부분 구현/누락/실행 미확인/보류·제외를 분류한다. Skill의 의미 판단·사용자 승인 절차도 실제 구현이며 Core 자동화 부재와 구분한다.
3. 승인된 범위에서 누락·불일치를 구현하고 의미 있는 정상·차단·실패 테스트를 실행한다. 기존 Spec Kit·프로젝트 검사와 Core를 재사용한다.
4. 테스트 통과 후 설계 원문과 **다시** 대조한다. 단순 명령 존재나 성공 예시만으로 충족시키지 않는다. CLI 연결, 영속 기록, 상태·증거 유효성, Skill 호출, 설치·버전 경로까지 확인한다.
5. 누락·실패가 있으면 고치고 관련 검증을 재실행한 뒤 다시 4단계로 돌아간다. 설계를 구현에 맞춰 삭제·완화해서 통과시키지 않는다. 입력·정책 충돌 또는 사용자 결정이 필요한 항목은 이유와 선택지를 남긴다.
6. 대응표에서 범위 내 미충족 구현이 없어야 완료한다. 실행 환경·접근 권한이 없어 확인하지 못한 항목은 미확인으로 명시하고 전체 검증 완료로 보고하지 않는다. 보류·제외 기능은 구현 누락으로 재개설하지 않는다.

## 완료 증거와 운영

검증 보고서는 설계 위치/기대 계약/구현 파일·명령/테스트·실제 결과/판정/남은 제약을 대응시킨다. 주제별 명세를 통째로 복사하지 않는다. Core·Skill 배포 버전과 설치 업그레이드를 함께 검증하고 Markdown·HTML 링크·생성물 동기화를 확인한다. Git Commit·Push·Merge·Rollback·태그는 명시적인 사용자 요청 없이 실행하지 않는다. 설계 버전 변경은 별도로 사용자 선택을 받으며 이번 작업의 설계 버전은 사용자 선택에 따라 1.0을 유지한다.
