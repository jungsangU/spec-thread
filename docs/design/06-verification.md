# 06 검증과 정합성

| 검증 | 질문 | 실행 주체 |
| --- | --- | --- |
| Discovery Gate | 분리·통합 전후에 요구사항, 예외 및 계약이 보존되는가. Brownfield 명세는 현행 근거와 맞는가 | 에이전트의 의미 검토와 공식 명세 품질 검사 |
| 명세 품질 | 요구사항이 명확하고 측정 가능한가 | 공식 체크리스트 흐름. 사용자 정의 체크리스트의 검토 상태는 검토자가 관리 |
| 산출물·구현 분석 | 명세→계획→작업→구현이 일치하는가 | 에이전트가 공식 `analyze`·`converge`를 전제에 맞게 사용 |
| 동작 | 프로젝트 테스트·빌드·정적 검사가 통과하는가 | 프로젝트 검증 명령 |
| 구조 | UUID, 상태, 경로, 참조가 유효한가 | `sdd-core validate` |
| 통합 | 검토한 후보가 통과했고 게시되는 트리와 동일한가 | 영향 분석을 수행하는 에이전트와 Core의 임시 통합·Git 검사 |

**개발 완료의 현재 코드**는 계획의 `findings`, `paths`, `checks`, `actual_features`, `evidence`를 사용한다. 입력 파일의 SHA-256을 검사 전후 비교한다. 경로는 정규화된 프로젝트 상대 경로이며 중복 제거 후 정렬한다. 경로와 파일 해시 쌍의 JSON을 다시 SHA-256으로 해시한다. 검사 성공과 해시 동일성이 확인되면 Work Item 상태 및 최종 기록을 저장한다.

구조 검증은 파일 매핑의 의미나 증거의 사실성, 기존 검증의 현재 유효성을 자동 판정하지 않는다. 이력에는 전체 파일 목록과 검사별 연관 정보가 저장되지 않는다. 따라서 영향 기반 선택적 재검증은 설계 정책이며 CLI에 캐시가 구현된 상태는 아니다. 검증 환경의 불변성은 사용자 운영 전제다.

**통합 검증**은 이전 Work Item의 로컬 통과를 재사용해 건너뛰지 않는다. 사용자가 검토한 기준과 후보 트리를 다시 구성하고 검증 계획에 제출한 전체 명령을 실행한다. 검증 세트의 충분성과 계획에 들어간 영향 근거는 프로젝트와 에이전트가 확인한다. Git은 검사된 트리의 동일성과 대상 브랜치의 기대 기준을 보장하는 데 사용한다.
