# 대화형 질문과 단계 연결

설계 1.1. 사용자는 시작 명령이나 자연어 요청으로 작업을 시작하고, 그 뒤에는 현재 단계 안내와 구체적인 다음 제안에 답하며 이어간다. 이 문서는 대화 UX와 표시 방식의 원본이다. Core의 [분석](03-analysis-standard.md)·[개발 상태](04-artifact-lifecycle.md)·[Gate](06-verification.md)·[승인형 Sync](reconciliation.md) 계약은 그대로 유지한다.

## 초기 질문

먼저 기존 자료와 이전 답변을 확인한다. Greenfield에서는 목적·사용자 → 주요 사용 흐름 → 핵심 동작 → 제약 → Feature 경계를 필요한 만큼 좁혀 간다. 고정 설문을 끝까지 채우는 절차가 아니라 **현재 부족한 판단 하나**를 묻고 답을 기다리는 방식이다. 프로젝트 설명·전체 기능·기술 제약을 한꺼번에 입력하도록 요구하지 않는다.

Greenfield에서는 목적과 초기 맥락이 충분해지면 공식 초기 명세를 먼저 만들고, 전체 업무 흐름 분석·잠정 Feature 분리·상세 질문을 이어간다. 초기 질문 UX가 확정된 Discovery 순서를 바꾸거나 완성된 설문을 초기 명세 생성의 전제로 만들지 않는다.

질문 하나에 짧은 예시나 선택지 2~3개를 줄 수 있으며 자유 입력과 “아직 모름”도 받는다. 사용자 설명에 이미 있는 답은 재질문하지 않는다. 사용자가 처음부터 상세 설명을 주면 그 내용을 재사용하고 순차 설문을 강요하지 않는다. 모른다는 답은 근거로 승격하지 않고 핵심 불확실성은 기존 Gate로 차단한다.

Brownfield에서는 코드·문서·테스트를 먼저 조사한다. 관찰한 현행 동작과 확인된 의도를 구분해 설명하고 사용자에게는 실제로 모호한 한 항목만 확인한다. 기존 기능 전체를 사용자가 다시 작성하도록 요구하거나 현행에 없는 기능을 임의로 추가하지 않는다. 충분한 초기 맥락을 얻으면 공식 specify/clarify를 재사용하고 나머지 질문을 점진적으로 해결한다. 공식 문서 형식·절차를 별도 설문 엔진으로 대체하지 않는다.

## 단계 이동과 승인

의미 있는 경계에서 현재 단계, 실제 결과, 다음 행동과 대상 범위를 짧게 보여준다. init 이후에는 개발 진입 검사(preflight develop)를 통과한 활성 Feature 하나를 제안한다. partial도 기존 대상·의존성 조건을 충족하면 제안할 수 있다. 차단된 대상을 준비 완료로 제시하지 않는다.

> **기능 정리 완료**
>
> ‘할 일 등록’의 범위와 개발 준비를 확인했습니다.
>
> 다음은 **기능 개발 · sdd-develop**입니다. 이 기능부터 진행할까요?

이 예시는 실제 준비 완료의 증거가 아니다. 구체적인 다음 제안 하나가 있을 때 “응”, “진행해”, “계속”으로 그 제안을 수락할 수 있다. 새 명령을 사용자가 다시 입력하도록 요구하지 않고 같은 에이전트에서 설치된 다음 Skill을 실행한다. 직접 호출 기능이 없으면 설치된 SKILL.md를 읽고 같은 절차를 따른다. 실행 자체가 불가능한 환경에서는 이유와 맥락을 채운 다음 명령 하나를 안내하며 실행했다고 가장하지 않는다.

여러 제안이 열려 있거나 입력·범위가 달라졌으면 짧은 동의가 무엇을 가리키는지 확인한다. 무응답은 동의가 아니다. 일반적인 단계 이동 동의가 Strict·범위 확대·필수 정책 완화·Sync 변경안·폐기·버전 변환의 구체적 승인 검토를 대체하지 않는다. 기존 정책 재사용과 일반 Gate 합성·재실행은 현재 개발 요청의 승인으로 진행한다.

한 번 승인한 개발 요청 안의 계획·구현·검증과 수정 가능한 오류의 재검증은 매 세부 명령마다 확인하지 않고 필요한 진행 안내와 함께 이어간다. 새 기능·범위 확대·중대한 의도 판단·필수 승인 경계에서만 필요한 확인을 받는다. Git 작업을 자동 다음 단계에 포함하지 않는다. [런타임의 작업 시작 검사](07-agent-runtime.md)로 읽기 전용 확인을 묶으며, 에이전트가 요구하는 명령 실행 권한은 그대로 적용한다.

보류·중단 요청은 다음 제안의 실행을 멈추고 파일·판단 근거를 보존한다. suspended는 실제 허용 전이에서만 사용하며 pending·failed·completed를 임의로 바꾸지 않는다. 재개 시 마지막 채팅 문장이 아니라 현재 산출물·기록·Gate를 다시 확인한다. 완료된 작업은 닫힌 상태로 두고 새 요청은 새 Work Item을 사용한다.

~~~mermaid
flowchart TD
  R["기존 자료·답변 확인"] --> Q{"지금 필요한 판단이 있는가?"}
  Q -->|있음| A["질문 하나 · 답변 대기"]
  A --> R
  Q -->|없음| W["현재 승인 범위의 작업·검증"]
  W --> G{"다음 단계의 Gate 충족?"}
  G -->|아니오| B["구체적 차단 사유·다음 질문"]
  B --> R
  G -->|예| P["결과 요약·구체적 다음 제안"]
  P --> U{"사용자의 응답"}
  U -->|동의| S["설치된 다음 Skill · 현재 조건 재확인"]
  S --> W
  U -->|보류| H["제안 보류·기록 보존"]
~~~

## 표시 형식과 채널 차이

기본 순서는 **현재 단계 → 핵심 결과/질문 → 다음 선택**이다. 짧은 단계 제목, 여백과 제한적인 강조를 사용하고 긴 로그·JSON·해시·명령 목록은 검토나 문제 해결에 필요할 때 제시한다. 질문은 하나씩 보여주며 실패 원인·영향·구체적 승인 내용은 생략하지 않는다.

터미널에서는 간결한 일반 텍스트를 기준으로 하고, 지원되는 화면에서만 Markdown·질문 선택 UI를 사용한다. 지원하지 않는 선택지를 실제 버튼처럼 표현하지 않는다. 거대한 ASCII 상자·반복 배너·장식용 이모지·가짜 진행률을 사용하지 않는다. 경로가 확정되지 않은 Discovery에 고정된 단계 수나 퍼센트를 만들지 않는다.

Codex와 Claude Code의 동일한 **정보 순서와 의미**를 목표로 하며 앱 전체의 색상·레이아웃·테마를 변경하거나 픽셀 단위로 같은 화면을 보장하지 않는다. 전역 output style이나 에이전트 설정을 덮어쓰지 않는다. 응답 지침은 모델이 따르는 지침이며 별도 GUI가 아니다. [Codex Skill](https://learn.chatgpt.com/docs/build-skills) · [Claude 출력 스타일](https://code.claude.com/docs/en/output-styles)

## 실행 지침 배포와 기록

공통 대화·표시 지침은 Core의 `skills/_conversation.md`에서 관리하고 bundle()이 세 네이티브 SKILL.md 뒤에 포함한다. 각 설치 파일은 자기완결적이며 별도 공개 Skill·명령을 추가하지 않는다. Codex·Claude에 같은 공통 본문이 설치되고 합성된 전체 내용의 해시로 설치·업데이트 정합성을 검사한다. 기존 확인된 Skill만 승인 업데이트하며 사용자 수정본은 덮어쓰지 않는다.

중요한 답·남은 질문·현재 실제 결과·다음 제안 범위는 기존 project.md/decisions.md 또는 해당 공식 산출물에 남긴다. 안내 기록은 Core 상태·승인 토큰의 원본이 아니며 실행 가능한 별도 상태 DB·자동 세션 복구·오케스트레이터를 만들지 않는다. 모델 응답의 실제 준수와 화면 경험은 실제 양쪽 에이전트 PoC로 별도 확인한다.

프로파일 분류·확장·반복 검사에 대한 실제 자동/예외 경계는 [검증 프로파일](verification-profiles.md)을 따른다. 일반 진행을 다시 승인받지 않고 간결한 분류 이유와 현재 검사만 안내한다. 중요 불확실성이나 Strict에서는 구체적 위험·범위·필수 검증을 제시하고 실제 답을 기다린다. 해시만으로 사람의 동의를 만들어 내지 않는다.
