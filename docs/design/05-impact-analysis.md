# 05 영향 분석과 위험도

영향 분석은 의미 판단이다. Baseline 인덱스는 후보를 빠르게 좁히고 실제 계약·구현 및 테스트가 판단의 근거를 제공한다.

현재 영향도 계산은 활성 Feature와 현재 계약을 대상으로 한다. 폐기 Feature의 과거 Source Map은 이력으로 보존한다. 병합·분할 후 활성 의존관계를 재평가하며, 부분 분석 상태의 개발 진입은 미분석 영역과의 핵심 의존성 위험 없음까지 확인한다.

1. 요청의 선언 Feature와 실제 변경 파일, 계약의 전후 동작을 대조한다. 파일 위치나 변경량만으로 중요도를 정하지 않고 공개 계약·데이터·보안·의존관계에 미치는 영향을 확인한다.
2. 변경 Feature에 의존하는 직접 소비자를 확인한다. 해당 계약의 영향이 계속 전파되는 경우 다음 의존 단계까지 진행한다. 영향이 없다는 근거가 생긴 경계에서 멈춘다. 영향이 확인된 Feature만 수정 대상으로 확장한다.
3. 여러 의존과 실제 순환을 표현할 수 있다. 이미 방문한 관계는 반복 조사하지 않는다. 순환 자체는 경고이고 중대한 계약·장애 위험이 확인될 때 차단한다. 역방향 간선은 정방향 관계로부터 계산하는 설계다.
4. 구현·계약 파일을 찾지 못하면 계약·호출부·테스트와 공식 산출물을 추가 조사한다. 근거와 검증 대상 범위를 기록하고 실제 변경과 재검증이 필요한 간접 영향 범위를 구분한다.

| 판정 | 조건과 처리 |
| --- | --- |
| `SAFE` | 변경 또는 영향 없음의 근거를 기록하고 필요한 범위 확장을 진행한다 |
| 비핵심 `UNKNOWN` | 추가 조사 후 남은 제한을 근거와 함께 기록한다. 초기화·개발 완료와 사용자 Git 반영 전 검토에서 필요한 재검증 후 허용 가능 |
| 핵심 `UNKNOWN` | 공개 계약, 보안, 데이터 무결성 등 중요한 판단의 근거가 부족하다. 해결 전 차단하며 사용자 승인만으로 통과시키지 않는다 |
| `CONFLICT` | 의도·구현 또는 통합 변경 사이의 실제 충돌이다. 상충하는 계약·산출물·구현 근거를 제시하고 사용자와 해결 후 재검증한다 |

예를 들어 저장 API의 반환 형식을 바꾸면 호출부의 파싱과 실패 처리를 검사한다. 어댑터가 동일한 외부 반환 계약을 유지한다는 근거를 찾았다면 그 지점에서 전파를 멈출 수 있다. 테스트 부재만으로 영향이 없다고 판단할 수는 없다.

이 판정은 변경의 위험도를 평가한다. Feature 확정은 [Discovery Gate](03-analysis-standard.md)에서 다룬다.

현재 Core는 제출된 `findings`의 판정·근거를 확인하고 차단 값에 실패한다. 영향 그래프 탐색, 중요도 판정, 누락된 소견 식별은 에이전트의 책임이다.

Source Map 경로의 이동·삭제·불일치는 실제 코드와 공식 산출물에서 재분석하여 교정한다. 해결되지 않은 핵심 참조는 Gate에 반영한다. `SAFE`에도 판단 근거를 남긴다. 이 판정은 분석·개발·사용자 통합 검토에 적용하며 Discovery에 필요한 근거로도 참조할 수 있다.

Core 소견 입력은 assessment/evidence와 필요한 critical을 갖는다. UNKNOWN의 critical이 생략됐거나 false 이외이면 핵심 UNKNOWN으로 차단한다. 명시적인 boolean false만 비핵심 경고로 허용한다. evidence는 비어 있지 않은 설명 문자열이며 실제 사실 확인의 책임은 Skill에 있다.


프로파일 분류는 이 영향 소견을 재사용한다. 국소 계약 유지 후보는 Lightweight, 관련 계약·Feature 확장은 Standard, 중요 계약/보안/데이터/전이 영향은 Strict 최소다. [정확한 위험 항목](verification-profiles.md)을 사용하며 파일 수나 변경 줄 수는 분류 기준이 아니다. 핵심 UNKNOWN/CONFLICT는 상향이나 승인으로 해소되지 않는다. 새 위험은 현재 Work Item의 필수 절차·검증을 추가하며 기존 필수 의무를 제거하지 않는다.

## 분석 범위와 종료 기준

분석 깊이 L1은 대상 Feature의 관련 요구·산출물·소스·테스트, L2는 직접 의존 Feature·계약, L3는 실제 영향이 전파되는 간접 의존, L4는 프로젝트 전체다. 테스트 실행 수준 L1~L4와 별개다. 대상부터 시작하고 계약·소비자·공통 제약의 실제 근거로 확장한다. Strict라는 이유만으로 전체 프로젝트를 읽지 않는다. 영향받는 Feature가 승인 범위를 벗어나면 기존 scope-expand 승인을 먼저 따른다.

features.yaml에서 대상·의존성, source-map.yaml에서 구현, verification.yaml에서 검증 정책, 현재 work-items.yaml에서 기존 판단을 찾는다. 긴 파일은 제목·검색·참조로 관련 부분부터 읽되 공통 제약·예외를 누락하지 않는다.

| 자료 | 우선 읽는 범위 |
| --- | --- |
| spec.md | 관련 요구·수용 조건 및 적용되는 공통 제약 |
| plan.md / tasks.md | 관련 기술 설계 / 현재 작업과 선행 작업 |
| contracts / data-model.md | 영향받는 인터페이스·데이터 |
| research.md / decisions.md | 현재 변경의 기술 판단·결정 |
| architecture.md / project.md | 적용되는 전역 제약·프로젝트 정책 |
| 다른 Feature 자료 | 실제 의존 영향 또는 추가 확인의 근거가 있는 부분 |

대상 Feature·요구사항, 적용 정책·제약, 직접 영향, 추가 영향이 없다는 충분한 경계 근거가 확인되고 중요한 불확실성·충돌이 없으면 탐색을 멈춘다. 근거가 부족하면 해당 영역만 확장한다. Core의 전체 Baseline 구조·참조 검사와 공식 Skill의 필수 읽기 범위는 축소하지 않는다. 별도 인덱스·벡터 DB·검색 시스템은 만들지 않는다.

## 동일 Work Item의 분석 사실 재사용

현재 세션·Work Item 소견·Baseline·Evidence·공식 산출물에서 이미 확인한 요구·계약·Feature·의존·설계·검증 방법을 다음 단계에도 사용한다. 단계가 바뀌었다는 이유로 전체 분석을 반복하지 않는다. 변경 전 코드의 테스트 PASS를 현재 PASS로 간주하는 것은 별개이며 [기존 Fingerprint 계약](06-verification.md)을 유지한다.

| 변화 | 다시 판단할 범위 |
| --- | --- |
| 요구사항·계약 변경 | 해당 요구·설계·계약과 소비자 |
| 신규 의존·불확실성 | 관련 영향 경계 |
| 구현 방식 변경 | 관련 설계·구현 |
| 검증 환경 변경 | 관련 방법·기존 결과 유효성 |
| 중단·재개·컨텍스트 유실 | 저장된 판단 근거의 현재 유효성과 부족한 근거 |

판단을 일괄 무효화하지 않는다. 의미적 현재성 판단은 Skill이 하고 기존 findings·evidence로 필요한 설명만 남긴다. Core에 환경 자동 탐지나 분석 캐시·컨텍스트 DB·중간 보고서를 추가하지 않는다.
